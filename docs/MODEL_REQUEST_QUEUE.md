# Text-to-SQL 모델 요청 대기열

2026-11-24 구현. 기존 Text-to-SQL 화면에서 SQL 모델 생성과 로컬 LLM 종합 의견 생성에 같은 FIFO 대기열을 사용한다.

- 동시에 실행하는 모델 요청: 1건.
- 실행 중인 요청을 제외한 최대 대기 요청: 3건.
- 따라서 처리 중 1건과 대기 3건이 있으면 다음 요청은 HTTP 429로 거절한다. 거절된 요청은 실행하지 않는다.
- 대기자는 “앞선 요청이 끝날 때까지 기다려 주세요. 현재 대기 N번입니다. 차례가 되면 자동으로 진행합니다.”를 확인한다.
- 앞선 요청이 성공하거나 실패하면 다음 요청을 자동으로 시작한다. 실패한 요청을 자동으로 재시도하지 않는다.
- 대기열이 가득 차면 “현재 모델 대기 요청이 3개입니다. 나중에 다시 이용해 주세요.”를 안내한다.
- 모델을 사용하지 않는 정형 조회, SQL 실행, 보고서 링크 조회 등은 모델 대기열을 점유하지 않는다.

## API와 권한

기존 generate/summarize POST에 `async_model: true`를 보내면 HTTP 202와 `model_job`을 돌려준다. 기존 화면은 응답의 `status_url`을 약 1초마다 GET하여 대기 순서, 처리 중, 완료/실패를 표시한다. 이 방식은 모델 완료까지 Waitress 요청 스레드를 점유하지 않는다. 완료되면 기존 결과 형식으로 화면 처리를 이어 간다. 종합 의견을 기다리거나 거절당해도 조회 결과 표를 확인할 수 있다.

기존 동기 API 호출도 같은 FIFO와 용량 제한을 따른다. `async_model`을 생략한 호출은 응답 형식 호환을 위해 완료까지 HTTP 연결을 유지하므로, 신규 연동에는 비동기 방식을 사용한다.

대기 접수에는 기존 로그인, 화면 권한 및 CSRF 검증을 적용한다. 작업 시작 시 계정 활성 상태와 조회 권한·범위를 다시 확인한다. 상태 및 결과는 접수한 사용자만 조회할 수 있고, 종합 의견 조회 권한도 재검증한다. 응답은 `no-store`이다. 모델 실행 완료 시 기존 사용 이력을 기록하며 대기 시간을 포함한 소요 시간을 남긴다. 상태 조회로 사용 이력을 중복 기록하지 않는다.

## 운영 범위와 한계

현재의 단일 Waitress 애플리케이션 프로세스에 적용하는 메모리 대기열이다. DB 스키마나 계산값, 데이터 조회 허용 공정을 변경하지 않는다. PE·VCM1·VCM2 검토 범위와 각 기능의 실제 조회 허용 범위는 별도로 확인해야 한다.

완료 결과는 최대 15분, 최근 128건을 보관한다. 페이지를 닫아도 이미 접수된 작업은 계속 처리한다. 서버 재시작 시 메모리 대기열이 초기화되며 재접수가 필요하다. 향후 여러 웹 프로세스나 여러 서버를 동시에 가동할 경우에는 공유 대기열과 단일 모델 작업자로 확장해야 전체 서버에서 1건 실행을 보장할 수 있다.

이 변경으로 운영 웹 서비스를 시작하지 않았다.

## 검증

- 대기열 단위 테스트 3건: FIFO, 1건 실행 + 3건 대기, 초과 접수 거절, 소유자 구분, 실패 후 다음 작업 처리, 완료 결과 정리.
- Text-to-SQL 관련 테스트 199건: 기존 조회·사용 이력 회귀 검사 포함. 신규 웹 테스트는 4명 접수 후 5번째 거절, 본인만 상태·결과 조회, SQL/종합 의견 공통 대기열, 대기 중 권한 회수 처리를 확인한다.
- 실제 브라우저에서 현재 템플릿과 JS를 로컬 파일로 열고 대기 API 응답을 모의하여 1440/768/390px에서 대기 순서, 자동 완료, 가득 찬 대기열 안내, 결과 표 유지와 가로 넘침을 확인한다. 실제 모델의 동시 사용자 부하 시험과 구분한다.

테스트는 iris2의 `.venv/Scripts/python.exe`로 실행한다. 운영 서비스는 중지 상태를 유지한다.
