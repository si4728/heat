# 검사 이력 및 차기 검사 권고 계획

2026-11-12 고객 개선 요청 4번을 구현했다. VCM 생산팀의 VCM1·VCM2를 대상으로 검사 이력을 연도별·공정별 두 화면으로 제공하고, 검사계획의 기본 화면에는 차기 검사 권고 설비만 표시한다.

## 검사 이력

- 연도별: `/inspections/yearly`. 검사 연도·VCM1/VCM2·공정·설비 검색으로 조회한다. 선택 연도의 설비별 검사 건수·최대 감육률·해당 최대값의 검사일을 표시하며 검사 없는 설비도 0건으로 구분한다.
- 공정별: `/inspections/process`. 설비 × 검사 연도의 최대 감육률을 비교한다. 연도별 최대값에 대한 최근 두 검사연도의 증감을 %p로 표시하며 동일 튜브의 감육속도로 해석하지 않는다.
- 검사일을 우선하고 없으면 보고일을 사용한다. 같은 해 여러 검사는 최대 감육률로 집계하며 그 값을 가진 검사 ID와 원본 PDF를 연결한다. PDF가 없으면 검사 상세로 연결한다.
- 대체된 검사 회차는 집계에서 제외한다. 측정값이 없으면 ‘－’, 실제 0이면 0.0으로 표시한다. 검사 결과의 유효 최대값이 없으면 보고서의 최대 감육률을 사용한다.
- 기존 검사 상세 검색과 튜브 이력은 화면 상단 링크로 유지한다.

## 권고 설비 및 등록

- 기본 화면: `/inspection-plans`. 권고 시기는 1년·2년·5년 이내 또는 전체 권고로 선택하며 기본은 2년 이내이다. 경과한 권고일도 포함하고 근거가 없는 설비는 제외한다.
- 권고 기준은 실측·통계 추정 중 빠른 날짜 / 실측 튜브 / 통계 추정 중 선택한다. 기본값은 두 방식 중 빠른 날짜이며 고정된 고객 승인 기준값으로 간주하지 않는다. 화면에서 선택한 근거와 실제 사용된 검사 기준일을 표시한다.
- 권고일은 그림 4에 따라 **해당 예측의 검사 기준일 + 최초 기준 도달까지 기간의 1/2**로 산정한다. 검사 당시 이미 기준 도달 상태이면 검사 기준일을 권고일로 표시하고 알 수 없는 최초 도달일을 만들어 표시하지 않는다.
- 통계 추정이 불가능할 때 기본 기준은 유효한 실측 예측으로 처리한다. 통계 추정만 선택하면 추정 근거가 없는 설비는 제외한다. 계산은 관리 참고용이며 기존 API 510 주기 계산과 별도이다.
- 행의 ‘+ 등록’을 열어 예정일과 **실제 검사 대상 Tube**를 선택하고 저장한다. Tube 목록은 열 때 조회한다. 임의의 수량만 입력하여 Tube를 자동 배정하지 않는다.
- 현재 번들의 사용 중 Tube만 등록한다. 실제 대상 목록·선택 당시 상태·신청자·권고 근거와 계획 이벤트를 기존 테이블에 저장한다. 수량만 먼저 저장하는 초안 기능은 이번 변경에 포함하지 않는다.
- 권고 등록 시 서버가 권고 대상과 사용 중 Tube를 다시 확인하고 설비 행을 잠가 동일 권고 설비의 중복 등록을 차단한다. Tube 상태도 잠금 조회 후 확인한다.
- 진행 중 계획이 있는 권고 설비에는 등록일과 확인 링크를 표시한다. 기존 신청·승인·검사 진행·완료 및 취소 절차는 `/inspection-plans?manage=1`에서 유지한다. 기존 계획 삭제나 상태 초기화는 없다.

## DB 및 권한

테이블·필드 추가와 데이터 마이그레이션은 없다. 기존 `inspection_plan_v2`, `inspection_plan_tube_target`, `inspection_plan_event`를 사용한다. 조회에는 INSPECTIONS 조회 권한, 등록에는 편집 권한과 CSRF 검증이 필요하다. 새 경로의 권한 매핑을 코드에 추가하여 운영 config 변경 없이 적용한다.

## 검증

- 새 화면·집계·권고 기준·윤년 경계·권한·CSRF와 기존 계산 관련 Python 시험 68건 통과.
- 개발 DB의 설비 212대·유효 검사 이력 425건을 확인하고 독립 SQL 개수 및 화면 집계의 일치를 검증했다. 기본 조건의 권고 대상은 28대였다. 수량은 개발 데이터 및 기준일에 따른 점검 결과이며 운영에 고정하지 않는다.
- 인증된 연도별·공정별·권고 계획·기존 계획 관리 GET 응답 및 미인증 차단을 확인했다. 조회 전용 사용자의 등록 차단도 검증했다.
- 기존 `iris2_test_transition` 시험 DB에서 계획·실제 대상 Tube·이벤트 저장, 중복 등록 및 다른 설비 Tube 차단을 검증하고 모든 삽입을 롤백했다. 업무 DB에는 계획을 등록하지 않았다.
- 실제 데이터의 저장된 HTML을 이용해 1440/768/390px에서 두 이력 화면과 권고 목록의 9개 조합을 확인했다. 같은 행의 Tube 조회·선택·등록 버튼 활성화와 모바일 필터 영역을 검증했으며 브라우저에서는 POST를 보내지 않았다.
- 증거: Git 제외 경로 `reports/inspection-workspace-20261112/`.
