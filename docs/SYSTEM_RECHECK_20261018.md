# IRIS2 시스템 기능 재점검 결과

점검일: 2026년 10월 18일. 대상은 IRIS2의 MariaDB 업무 화면·접근 권한·검사계획·계산·파일·백업·복원·예약 실행이다. 기존 IRIS와 기존 Windows 작업은 변경하지 않았다.

## 점검 결과

| 항목 | 결과 |
|---|---|
| 업무·보안·계산·백업 회귀시험 | 79개 통과, 실패·오류·생략 0개 |
| 인증된 조회 경로 | 48개 정상 응답 |
| 수동 백업 | 실제 실행 서버의 백업 화면에서 성공 |
| 예약 실행 | 별도 점검 경로에서 실제 백업 1회 성공, 두 번째 실행은 건너뜀 |
| 새 백업 복원 | 네 스키마를 별도 복원하고 전체 데이터·테이블·뷰·트리거·루틴 기준값 비교 통과 |
| 구형 백업 복원 | 네 스키마 구조 검증 통과. 전체 데이터 기준값이 없는 구형 형식은 제한 검증으로 표시 |
| 복원본 접근 권한 | 앱 계정 접속·DML 권한 확인, 분석 계정의 쓰기 차단 확인 |

| 원본 보호 | 기존 IRIS 소스 315개 파일 해시 일치 |

설비 902대, 검사 435건, 튜브 결과 6,084건, 물리 튜브 2,253개를 확인했다. 쓰기 Workflow 시험은 별도 시험 DB에서 수행했으며 운영 DB 덮어쓰기는 하지 않았다.

## 발견하고 수정한 문제

1. 복원 성공 로그가 예약 백업 성공으로 계산될 수 있었다. 백업 작업과 복원 검증 작업을 분리했다.
2. 백업 파일이 삭제되거나 손상되어도 과거 성공 로그로 예약 실행을 생략할 수 있었다. 파일 위치·존재·크기·체크섬을 확인한다.
3. 설정 파일의 문자열 `false`가 참으로 해석될 수 있었다. 명시적인 Boolean 변환을 적용했다.
4. 스케줄 시각이 PC 시간대에 의존했다. 한국시간 `Asia/Seoul`로 계산하며 주간 일정과 30분 재시도를 시험했다.
5. 예약 작업과 수동 작업의 중복 방지가 한 프로세스에만 적용되었다. 프로세스 간 파일 잠금을 추가하고 실행 직전 일정을 다시 확인한다.
6. 스케줄러 오류가 기록 없이 사라질 수 있었다. 상태 파일·최근 확인 시각·오류 상태를 남기고 화면에 표시한다.
7. 기존 복원 성공 판정은 SQL 파일 체크섬과 클라이언트 종료 결과만 확인했다. 새 형식은 데이터와 SQL 정의의 기준값을 저장하고 복원 후 전수 비교한다.
8. 백업 대상 스키마가 코드에 고정되어 있었다. 현재 업무용 config의 네 스키마 연결 정보를 사용한다.
9. 오래된 백업 파일 정리에 실패하면 새 백업까지 실패로 기록될 수 있었다. 정상 백업은 보존하고 정리 실패를 별도 경고로 남긴다.
10. 복원본에 앱 계정 권한이 없으면 설정을 전환해도 사용할 수 없었다. 전용 앱·분석 계정 권한을 부여하고 접속을 확인한다.
11. 이전 서버 재시작에서 Python 하위 프로세스가 남고 Windows 포트 재사용으로 두 버전이 함께 동작할 수 있었다. 배타적 소켓과 검증된 실행 프로세스 재시작 절차를 적용했다.
12. `app.py` 직접 실행 경로에 오래된 실행 코드가 남아 있었다. 공통 실행 진입점으로 연결하고 상태 점검 실행을 확인했다.

백업 형식은 v2로 개선했다. 백업 도중 원본 데이터가 변하면 해당 백업에 현재 DB의 기준값을 잘못 연결하지 않는다. 이런 경우와 구형 v1 백업은 복원 후 구조 검증 범위를 명시하며, 전체 검증으로 표시하지 않는다.

## 현재 자동화 설정

- 예약 백업: 사용
- 주기: 매일 한국시간 02:00
- 보관: 최근 30개 백업 파일
- 예약 실패: 30분 후 재시도
- 서버 중지 중 놓친 일정: 다음 실행 때 보충 백업 여부 판단
- 스케줄러 점검 간격: 30초
- 다음 예약 시각은 백업 관리 화면과 `backups/scheduler_status.json`에서 확인

## 자동화 범위와 남은 운영 구성

**현재 예약 백업은 IRIS2 웹 서버가 실행 중일 때 동작한다. IRIS2용 Windows 작업이나 서비스의 재부팅 자동 시작은 등록되어 있지 않다.** 기존 `IRIS Heat Exchanger Server` 및 주간 보고 작업은 IRIS2를 실행하는 작업이 아니며 변경하지 않았다.

`tools/run_scheduled_backup.py`를 외부 작업 스케줄러에서 실행할 수 있도록 준비했다. 이 파일을 만든 것만으로 Windows 작업이 등록되지는 않는다. 별도 실행 시에도 동일한 프로세스 간 잠금과 중복 방지 규칙을 사용한다.

복원 기능은 별도 스키마를 생성해 검증하고 유지한다. 현재 업무 DB를 자동으로 덮어쓰거나 자동 전환하지 않는다. 운영 복구에는 입력 중지, 복원 검증, 앱·분석 계정 권한 확인, config 연결 대상 변경, 앱 재시작과 접속 확인이 필요하다. 복원용 스키마 정리는 별도 관리 대상이다.

백업 범위는 네 MariaDB 업무·검토 스키마이다. PDF·JSON·C-Scan·프로그램 소스·DB 접속 config와 MariaDB 서버 계정 자체는 포함하지 않는다. 이 파일들과 계정 복구 정보는 별도로 보존해야 한다.

PC 콜드 부팅, 운영 MariaDB의 강제 중단·자동 재시작, 실제 현장 LAN 장기 부하는 이번에 수행하지 않았다. 로컬 LLM 모델 독립 실행 및 공학 승인·현장 사용자 인수는 기존의 별도 확인 항목이다. 이번 자동시험을 이 항목의 완료로 간주하지 않는다.

## 실행·재점검 명령

```powershell
cd C:\access\heat\iris2
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\start_mariadb.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\run.ps1
```

실행 중인 IRIS2만 재시작하려면 다음 명령을 사용한다.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\restart_iris2.ps1
```

검증 명령은 다음과 같다.

```powershell
.\.venv\Scripts\python.exe tools/run_validation.py
.\.venv\Scripts\python.exe tools/transition_smoke.py
.\.venv\Scripts\python.exe tools/run_scheduled_backup.py
```

마지막 명령은 현재 일정이 실행 대상일 때 실제 백업을 수행한다. 시험용 단순 조회 명령이 아니다.

상세 증거는 `reports/system_recheck`에 보관했다. 백업·복원 실험, 실제 예약 실행, 구형 복원, 계정 접근 권한, 실행 화면 검증, DB 무결성 결과를 분리해 기록했다. 전체 시험과 조회 경로 결과는 `reports/mariadb_transition/validation.json` 및 `route_smoke.json`에 있다.
