# 운영 현황 데이터 보정 Plugging 및 Text-to-SQL 적용 검토

2026-11-24 · 검토 소스 `70343e7` · iris2 로컬 MariaDB와 보관 PDF 기준

네 요청 모두 적용 가능한 방향이다. 다만 화면 분류 변경, 원본 데이터 보정, 실제 정비 기록, 계산 결과 조회를 나누어 적용해야 한다. 특히 **이미 등록된 검사일을 다시 채우는 작업**, **공칭두께를 실측 최소두께로 일괄 대입하는 작업**, **개별 튜브 기준 도달을 설비 전체 20% 도달로 표시하는 작업**은 피해야 한다.

이번 작업은 분석이다. 운영 데이터·계산 코드·DB 스키마를 변경하지 않았고 웹 서버를 시작하지 않았다. 원본 PDF 추출·화면 이미지·상세 진단 JSON은 비공개 로컬 `reports/review_20261124/`에만 보관한다. 이 문서의 PE 검토는 사용자가 지정한 기존 PE 검사 10대의 확장 가능성 검토이며 VCM3·VCM4 개발을 포함하지 않는다.

## 2. 잔여수명 구간 변경

### 현재 규모와 변경 후 예상

현재 운영 현황은 VCM3·VCM4를 제외한 등록 설비 900대를 집계한다. 그중 IRIS 이력이 있는 설비는 VCM 생산팀 108대, PE 10대, 합계 118대다.

| 표시 구간 | 현재 | 표시 분류만 변경한 뒤 |
| --- | ---: | ---: |
| 15년 초과 | 64 | 64 |
| 5년 초과~15년 이하 | 10 | 10 |
| 5년 이하 | 9 | 9 |
| 산정 불가 | 787 | 35 |
| 한도 미도달 | 30 | 산정 불가로 통합 |
| IRIS 미실시 | 없음 | 782 |
| 전체 | 900 | 900 |

이 수량은 **현재 데이터에서 표시만 재분류한 기준**이다. PE 통계 추정 활성화·원본 보정·실제 Plugging 반영 후에는 달라진다. VCM1·VCM2만 보면 212대 중 이력 없음 104대, 검사는 했으나 수명 수치가 없는 설비 25대가 해당한다.

### 적용 방법

1. 설비 단위의 등록 IRIS 검사 이력 존재 여부를 먼저 판정한다. `reason_counts.NO_INSPECTION`은 미검사 **튜브** 수이므로 설비의 IRIS 미실시 여부로 쓰지 않는다. 검사일이 없거나 결과가 부적격인 검사 기록도 이력이 없는 설비와 구분한다.
2. 이력이 없으면 표시 구간은 `IRIS 미실시`다. 의미는 ‘시스템에 IRIS 이력 미등록’으로 안내한다. 현실에서 실제 검사를 하지 않았다는 단정은 피하며 IRIS 비적용 설비는 적용 대상 상태도 함께 표시한다.
3. 이력이 있고 잔여수명이 수치로 산정됐으면 기존 long/medium/short를 유지한다. 0년은 short이며 미산정과 다르다.
4. 이력이 있지만 수치가 없으면 unknown으로 표시하고 not_reached를 화면에서 합친다. 내부 `LIMIT_NOT_REACHED`, `INSUFFICIENT_DATA`, 통계 추정 상태·원시 예측일은 보존한다.
5. 설비 목록과 내려받기에 주 사유와 보조 사유를 표시한다. 예: `감육 미검출 · 양의 감육속도 미확보`, `유효 표본 10본 미만`, `두께 원본 확인 필요`, `복수 검사 집단 식별 필요`, `가용 데이터에서 한도 도달 시점 미산정`.

E-13은 표본 5본과 감육 미검출 사유가 함께 존재한다. 사유 하나만 저장하거나 표본 부족을 감육속도 오류로 치환하지 않는다. E-122A·E-341·E-222는 최신 표본의 감육률 분산이 없어 `DEGENERATE_SAMPLE`이다. 과거 검사에는 양의 감육률이 있으므로 ‘모든 과거 측정이 0%’로 설명하면 잘못이다.

영향 파일은 `application/life_dashboard.py`, `application/equipment_summary.py`, `services.dashboard_remaining_life`, 대시보드 표·필터·Excel/보고서, Text-to-SQL 상태 집계다. 특히 종합 의견은 내부 한도 미도달과 미산정을 현재 구분하므로 표시 구간 통합과 의미 구분을 함께 유지해야 한다. 기존 not_reached 필터 링크는 새 필터로 호환 처리한다.

E-222의 2025년 PDF 120쪽은 Thickness 2.40mm, Design Th'k 2.11mm와 NDD를 명시하며 현재 최소두께는 NULL이다. 반면 2022년 자료의 공칭두께는 2.77mm다. 수량 정정과 별개로 해당 회차의 두께 기준도 대조 대상이다. 과거 공칭두께를 사용해 2025년 감육률을 임의 재계산하거나 원본의 0%를 덮어쓰지 않는다.

현재 E-222 등록 튜브는 22개로 179보다 적지만, 이것만으로 설계 총수가 179라고 확정할 수는 없다. 도면·bundle 정체성·이전 사양과의 관계를 함께 확인해야 한다. 수량이 328→179로 바뀌면 20% 한도 분모와 정수 허용 개수, 미등록 수량, 표본 추정 최대값, Map의 기본 표시 슬롯, 잔여수명이 모두 달라질 수 있다. 예를 들어 기존 `> floor(총수×20%)` 규칙에서는 초과 판정 개수가 66본에서 36본으로 바뀐다. ‘도달’의 비교 연산자 자체도 이 작업에서 몰래 바꾸지 않는다.

보정은 공통적으로 dry-run 목록→별도 `iris2_test_*` 복원본 시험→전후 대조→백업→운영 적용 순서가 필요하다. 예상 기존 값이 다르면 중단하고, 재실행 시 중복 revision을 만들지 않아야 한다. 적재 원본 JSON·과거 사양·원본 PDF는 보존하며 운영 SQLite는 보정/이관 원본으로 사용하지 않는다.

## 4. PE 생산팀과 기준 도달 표시

### 검사일은 이미 존재한다

PE 2020년 검사 10대의 inspection_date와 report_date는 모두 등록돼 있다. 현재 통계 추정이 빠지는 직접 원인은 `services.py`의 `process.unit_code in ('VCM1','VCM2')` 조건이다. 존재하지 않는 추정 결과를 화면이 ‘검사일 미등록’처럼 설명한다면 그 설명도 함께 고쳐야 한다. 날짜를 새로 채워 넣는 것으로 해결되지 않는다.

### 개별 튜브 도달과 설비 한도 도달은 다르다

대시보드에는 기존 대표 잔여수명과 별도로 `실측 기준 도달 튜브 있음`, `검사일 기준 추정상 도달`, `예측 도달일 경과` 배지를 해당 근거와 함께 표시하는 방법을 권장한다. 도달 상태를 정비 완료로 표시하지 않는다. 나머지 PE 4대 중 ER-201은 표본 11본으로 추정 가능하고 ER-301A/B·E-331D는 표본 부족이다. 표본 수 제한을 낮춰 일괄 산정하지 않는다.

### 먼 미래 연도 표시

VCM1 E-331A는 대표 잔여수명에 `30년 이상`을 표시하면서 보조 `target_display`에 `2321년`이 남는 것을 재현했다. 원인은 `equipment_summary.py`의 실측 기준 분기가 `life_reached_year`를 원시 연도로 출력하기 때문이다. 통계 추정만이 아니라 실측 기준 보조 문구에도 공통 표시 함수를 적용한다. 원시 연도·날짜는 계산 근거로 보존하고 화면·Excel·Text-to-SQL의 표시만 통일한다. 같은 E-331A 코드의 PE 미검사 설비도 있으므로 VCM1 대상임을 확정한다.

## 5. 분석 화면 Plugging 완료 및 취소

### 재사용 가능한 부분과 부족한 부분

현재 단일/일괄 튜브 상태 변경 API와 `PLUGGED` 색상, `actual_plugged_count`, `ALREADY_PLUGGED` 예측 행은 존재한다. 따라서 Map과 계산을 처음부터 다시 만들 필요는 없다.

다만 기존 상태 변경은 `current_status`와 이벤트 사유만 바꾸며 `plugging_date`를 입력하지 않는다. `tube_lifecycle_event`에는 현재 작업일·등록일·등록자 컬럼이 없고, `maintenance_record.action_date`도 실제 입력일로 기본 생성되며 등록자를 충분히 보존하지 못한다. `web/access_audit`는 보조 접근 이력이지 튜브별 정비 완료 원장을 대신하지 못한다.

### 권장 설계

- 기존 분석 화면의 Tube Map 선택을 재사용하여 ‘선택 튜브 Plugging 완료 등록’과 등록 이력/취소 조작을 추가한다. 별도 화면 신설은 필수가 아니다.
- 완료 일자, 사유/작업 근거, 서버 세션의 등록자, 등록 시각, 작업 묶음 ID를 기록한다. 등록자가 보낸 사용자 ID를 신뢰하지 않는다. 실제 완료 일자는 DATE, 등록 시각은 UTC timestamp로 구분한다.
- 완료 이벤트와 원본 이벤트를 참조하는 취소 이벤트를 추가 전용 원장에 남긴다. 잘못 입력한 기록 취소와 실제 Plug 제거/튜브 교체는 서로 다른 작업이다. 취소 시 이력을 삭제하거나 무조건 IN_SERVICE로 되돌리지 않는다.
- 한 트랜잭션에서 해당 설비·현재 bundle 소속의 실제 등록 튜브만 잠그고 원장과 현재 상태·완료 일자를 반영한다. Map의 임의 추정 슬롯/가상 튜브는 완료 대상으로 받지 않는다. 중복 선택을 제거하고 원자적 일괄 적용, 요청 멱등성, 상태 버전 충돌을 검사한다.
- 미래 일자는 완료가 아닌 계획이므로 완료 API에서 거절한다. 설치일 이전·퇴역 bundle·다른 설비 튜브·원본 완료가 아닌 이력 취소를 거절한다. 기존 날짜 미상 PLUGGED는 임의의 오늘 날짜로 소급 보정하지 않고 별도 확인 상태로 둔다.
- 정비/튜브 변경 권한과 CSRF를 검증한다. 분석 조회 권한만 있는 사용자는 완료/취소할 수 없어야 한다. 실제 적용 권한 키는 기존 EXCHANGERS 편집과 MAINTENANCE 정책을 통합해 명시한다.

### 계산 영향과 가장 큰 위험

1. 실제 완료는 모델 예측보다 우선한다. 완료일 이후의 누적 수량은 최소한 실제 완료 수량을 포함해야 한다.
2. 실제 완료, 실측 기준 도달, 향후 예상 수량을 분리해 이중 집계하지 않는다. 개별 튜브가 이미 완료됐다면 예상분에 다시 추가하지 않는다.
3. **현재 대표값은 통계 추정이 유효하면 이를 우선한다.** 실제 완료 수량이 설비 한도를 넘었는데 추정값이 미래라면 과대 수명이 표시될 수 있으므로 실제 완료 하한과 대표값 우선순위를 함께 보강해야 한다. 상태 입력 UI만 추가하고 끝낼 수 없다.
4. 과거 기준일 계산은 해당 기준일 이전의 유효 완료 이벤트로 재구성해야 한다. 현재 status만 사용하면 미래 작업이 과거 통계에 섞인다. 취소의 의미도 오등록 정정인지 실제 작업일의 상태 변경인지 구분한다.
5. 원장 추가 테이블은 DB revision/Excel 캐시/계산 스냅샷 무효화 대상에 포함한다. 기존 DB revision 트리거가 새 테이블에도 자동 존재한다고 가정하지 않는다.
6. 실제 Plugging이 공학적 검사 권고를 자동 소멸시키는 것은 아니다. 기존 API 510 승인 이력이나 검사계획을 함께 덮어쓰지 않는다.

위 변경은 새 원장/취소 관계/인덱스/현재 상태 버전 등 추가형 DB 마이그레이션이 필요한 높은 영향 작업이다. 별도 복원 DB에서 중복 등록·동시 취소·부분 실패·두 번 클릭·날짜 경계·U-tube 두 끝 중복 선택·교체 이후 취소를 검증한 뒤 운영 적용해야 한다.

## 6. Text-to-SQL 보완

### 이미 구현된 범위

현재 작업 소스에는 설비별 1행, 최대 감육률 순위, 조건 해당 튜브 수, 생산팀·공정·설비명·최근 검사일, 분석 화면과 동일한 잔여수명·권고일, 분석 링크, 로컬 LLM 종합 의견이 있다. 내부 ID는 표시 컬럼 대신 링크·중복 방지·권한 검증에만 사용한다.

이는 `prod/20261123-equipment-query`의 `70343e7` 기준이며 main 병합/운영 웹 재가동을 완료했다는 의미는 아니다. 서비스가 중지 상태인 동안 새 기능을 운영 화면에서 확인했다고 말하면 안 된다. 추가 예시 질문별 미지원 범위는 `TEXT_TO_SQL_EQUIPMENT_RESULTS_20261123.md`에 구분돼 있다.

### 계산값 DB 저장은 선택 가능하지만 버전이 필요하다

현재는 분석 서비스를 재사용해 조회 시 계산하므로 DB에 수명을 저장하지 않아도 ‘5년 이하’ 조건이 가능하다. 반복 조회·집계 SQL·응답 시간 개선에는 계산 결과 스냅샷이 유용하지만, 설비 테이블에 잔여수명 숫자만 덮어쓰는 방식은 권장하지 않는다.

권장 구조는 다음과 같다.

| 저장 단위 | 필수 내용 |
| --- | --- |
| 계산 실행 | run ID, 기준일, 완료 상태, 알고리즘/모델 버전, 원본 DB revision, 공개 계산 설정 해시, 생성 시각 |
| 설비별 결과 | 설비 ID, 생산팀/공정, 최근 검사일, 잔여기간, 원시 상태, 표시 구간, 사유 코드, 실제 완료/기준 도달 수량, 권고일과 근거 |
| 최신 유효 결과 연결 | 같은 기준일·설정·알고리즘의 완결된 run만 공개하는 포인터/뷰. 이전 run은 이력으로 보관 |

검사·설치일·사양·수량·튜브 상태·Plugging 완료/취소·판정 기준이 바뀌면 stale로 처리한다. 기준일이 하루 바뀌는 경우도 확인한다. 여기서 모델 버전은 수명 계산·통계 추정 모델을 뜻하며, 로컬 LLM 모델을 바꾼다고 잔여수명 수치가 달라져서는 안 된다. 의견 생성 모델/프롬프트 버전은 별도로 관리한다. 단일 일관된 읽기 스냅샷에서 계산하고 공개 전 원본 revision을 대조해야 한다. 현재 설비별 서비스 호출은 하나의 전체 DB 스냅샷을 공유하지 않으므로 이 부분의 배치 계산 리팩터링도 필요하다.

질의는 `remaining_life_years <= 5`뿐 아니라 유효 run·기준일·설비 권한·산정 상태를 함께 제한한다. NULL을 0으로 변환하지 않는다. 한도 미도달의 표시 통합 후에도 내부 상태는 보존한다. Text-to-SQL DB 계정에는 승인된 결과 뷰의 SELECT만 추가하고 쓰기 권한을 주지 않는다. stale 시 실시간 재계산 또는 기준일/이전 결과 표시 중 어떤 정책을 쓸지 정해야 한다.

### 생산팀 범위 확대

현재 `text_to_sql_service.catalog()`는 VCM1·VCM2만 허용한다. UI만 PE를 보여줘서는 안 되며 catalog, 검사 범위 선정, 계산 대상, 쿼리 검증, 실행 시 재인가, 도움말·회귀시험을 함께 변경해야 한다.

이번 PE 검사 10대는 명시된 확장 대상으로 검증할 수 있다. PVC·가소제 등 나머지 팀 전체까지의 공개 범위는 별도 대상 목록을 확정한다. 모든 새 공정을 자동 허용하는 방식 대신 설정 가능한 양의 허용 목록과 사용자 조회 권한을 사용한다. VCM3·VCM4는 계속 제외한다.

### 동시 사용자와 모델 대기

현재 오류는 Flask 프로세스의 `generation_lock.acquire(blocking=False)` 때문이며 일반 SQL 모델 생성과 종합 의견 생성이 같은 잠금을 공유한다. 반면 새 설비별 계산 조회·유체 집계·PDF 조회 등의 결정형 경로는 모델 생성 잠금을 사용하지 않는다. 모든 조회를 같은 병목으로 보면 안 된다.

1. 결정형 DB/계산 조회와 LLM 추론의 처리 용량을 분리한다.
2. LLM 작업은 제한된 비동기 대기열에 넣고 즉시 job ID를 반환한다. 기존 Text-to-SQL 화면에서 대기 순서·실행 중·완료·실패·취소를 표시한다. 대기 때문에 Waitress 요청 스레드를 장시간 점유하지 않도록 한다.
3. 최초에는 모델 worker 1개를 유지하고 생성 SQL과 종합 의견을 공정하게 배분한다. 종합 의견이 새 SQL 생성을 계속 막지 않게 한다. 사용자별 대기 개수·전체 대기열 길이·대기 시간·추론 시간 제한을 둔다. 대기열이 가득 찬 경우에는 명확히 안내하며 무제한으로 쌓지 않는다.
4. job 조회/취소는 소유자와 현재 설비 권한을 재확인한다. 서명 토큰의 15분 유효기간은 대기 시간과 실행 완료 시점을 고려한다. 프로세스 재시작 때 작업 복구/실패 처리 기준도 필요하다.
5. 모델은 현재 worker마다 CPU 스레드 8개를 사용한다. 동시 모델 수만 늘리면 CPU·RAM·DB 경합과 응답 지연이 커질 수 있다. 대표 질문으로 동시 사용자 시험 후 worker 수·스레드·캐시를 조정한다.

이 방식은 ‘즉시 거절’을 ‘진행 상태가 보이는 순차 처리’로 바꾸는 것이다. 실제 병렬 추론은 별도의 자원 검증 항목이다. Waitress의 task queue 경고와 앱 내부의 LLM 잠금은 서로 다른 대기열이다.
