# Text-to-SQL 조회·결과 활용 개선

2026-11-27. 기존 조회 범위와 SELECT 전용 계정·서명·권한을 유지한다.

이번 보완은 복합 조건 조회, 실행 전 해석 조건 표시, 유체 조건의 설비별 목록·분석 링크, 화면 결과 Excel 내보내기 네 항목이다. 기존 화면과 API 흐름을 확장했으며 별도 화면은 만들지 않았다.

## 반영 내용

- 현재 승인 Tube 사양의 Cu-Ni 재질 조건에 최대 감육률·잔여수명 조건을 AND로 결합한다. 질문에 지정한 공정과 화면 선택 범위는 기존 교집합 선택을 사용한다. 감육률 미산정·수명 미산정은 수치 조건에 포함하지 않고, 실제 0은 보존한다.
- 예: `VCM1에서 Tube 재질이 Cu-Ni이고 최대 감육률 30% 이상이며 잔여수명 5년 이하인 열교환기 목록`. 다른 재질·OR·제외 조건·운전조건·고급 이력 조건의 임의 결합은 이번 범위가 아니다.
- SQL 생성 후 실행 전에 조회 공정, 재질, 수치 비교 조건, AND 적용, 표시 상한과 현재 분석값 기준을 표시한다. 계산 조건은 서명한 설정으로 실행하며 표시 문구로 계산을 대체하지 않는다.
- `Shell 유체명이 STEAM인 열교환기 목록`은 설비별 한 행과 분석 링크를 제공한다. 복수 측이 같은 설비에 해당하면 측과 유체명을 한 행에 합친다. 집계·수량·유체명별 질문은 기존 그룹 집계를 유지한다. `S:STEAM` 정규화는 양쪽 경로에서 동일하다.
- 실행 결과의 `Excel 내보내기`는 질문, 조회 시각, 해석 조건, 설비 범위, 표시 행 수·잘림 여부, 계산 기준일과 표 데이터를 담는다. SQL을 재실행하거나 클라이언트의 행 데이터를 신뢰하지 않고 서버가 보관한 화면 결과를 사용한다. 0과 결측을 구분하고 텍스트를 수식으로 실행하지 않는다.

## 접근·보관

다운로드는 로그인·Text-to-SQL·검사 조회 권한과 CSRF를 검증한다. 설비 분석은 열교환기·잔여수명 권한도 재검증한다. 현재 설비 카탈로그에서 접근 가능한 범위를 재확인하며 본인이 조회한 결과만 내려받을 수 있다. 사용 이력에 내보내기를 기록하고 응답은 `no-store`다.

완료 결과는 프로세스 메모리에 최대 32건, 15분간 보관한다. 상한 초과 시 오래된 결과부터 제거한다. 서버 재시작·만료·결과 제거 후에는 다시 조회해야 한다. 화면 표시 상한(설비 100행, 유체 500행 등)은 Excel에도 동일하게 적용한다. 전체 결과 내보내기나 영구 수명 스냅샷 저장 기능은 아니다.

## 검증

`tests/test_text_to_sql_enhancements.py`는 복합 조건의 실제 교집합, 미지원 조건 거절, 원본 결과 보관, 사용자 구분·만료·보관 상한, 수식 문자열 처리, HTTP 다운로드, CSRF·범위·권한 회수와 빈 결과를 확인한다. 유체 및 링크 회귀 검사도 변경된 목록 동작에 맞춰 보완했다.

MariaDB 의존 모듈을 제외한 관련 Python 회귀 검사 310개가 통과했다. JavaScript 문법·링크·차트 검사도 통과했다. 아래 브라우저 검사는 대체 데이터 기준으로 통과했다.

브라우저 재현:

```powershell
.\.venv\Scripts\python.exe tools/verify_text_sql_enhancements_browser.py
```

이 도구는 DB 초기화를 대체하고 시험용 설비·조회값·모델 응답을 사용한다. 실제 템플릿·JS·인증 HTTP·조건 파서·서명·Excel 생성 경로로 두 예시, 분석 링크, 다운로드, 질문 변경 시 이전 결과 비활성화, 1440/768/390px 가로 넘침을 검증한다. 내려받은 XLSX의 값도 다시 읽어 확인한다. 보고서·스크린샷·파일은 Git에 포함하지 않는 `reports/text-sql-enhancements-20261127/`에 보관한다.

## 이 PC의 첫 화면 오류 복구

초기에는 127.0.0.1:3307 연결이 거부되었고 이후 DB 연결이 복구되었다. 사용자가 보고한 첫 화면 `DATABASE_UNAVAILABLE`의 실제 원인은 이 PC에 `tube_plugging_event` 테이블이 없는 것이었다. 기본 health 응답은 이 추가 마이그레이션 누락을 검사하지 않으므로 health의 `ok`와 첫 화면 오류가 동시에 나타날 수 있었다.

로컬 네 스키마 백업(46,374,198 bytes, 복원 시험은 미수행)을 생성한 뒤 기존 `migration.plugging_operations.apply_migration`으로 원장 두 테이블과 보호·revision 트리거를 적용했다. 검사값·수량·날짜 보정 도구는 실행하지 않았다. 이후 실제 `http://localhost:4824/`를 인증된 읽기 요청으로 확인해 HTTP 200과 HTML 본문을 검증했다. 서비스 시작·중지·재시작은 수행하지 않았다.

읽기 전용 실제 DB 검증 도구:

```powershell
.\.venv\Scripts\python.exe tools/verify_text_sql_enhancements_readonly.py
```

VCM1의 Cu-Ni 설비 13대에서 감육률·잔여수명 복합 조건의 교집합은 실제 분석값과 일치했다(해당 두 수치 조건을 모두 만족하는 설비는 0대). 유체 조회는 최초에 Text-to-SQL 계정의 `heat_exchanger_spec_revision` SELECT 권한 누락으로 차단되었다. 자동 승인 검토에서 명시적 사용자 승인 필요로 거절된 뒤, 사용자가 아래 네 테이블 SELECT 추가를 명시적으로 승인하여 기존 권한 도구로 적용했다.

- `heat_exchanger_spec_revision`
- `heat_exchanger_side_spec`
- `iris_inspection_summary_history`
- `tube_plugging_event`

적용 후 SHOW GRANTS 검사에서 계정은 USAGE·SELECT만 보유하고 GRANT OPTION이 없음을 확인했다. 비밀번호·쓰기에 관한 권한은 변경하지 않았다. 실제 VCM1 STEAM 22대의 설비별 목록·집계가 일치했고, 인증된 HTTP 조회 결과 22행과 내려받은 XLSX 22행도 일치했다. 대시보드 HTTP 200을 재확인했다. `test_text_to_sql_mariadb.py` 10개, 임시 복제 DB에서 실행한 `test_text_to_sql_steam_mariadb.py` 1개가 통과했다. 기존 유체 목록 시험의 기대값을 새 설비별 한 행 동작에 맞춰 수정했다.

실제 모델 추론은 이번 작업에서 재검증하지 않았다. 소스 반영과 운영 배포·서비스 재시작은 별개다. 복구 이전 전체 MariaDB 회귀 실행은 누락 스키마·권한으로 실패했으므로 위 310개 통과 기록과 혼합해 전체 통합 통과로 해석하지 않는다.

## 다른 PC에서 반영할 때

1. 해당 PC의 로컬 변경을 보존하고 원격 소스를 갱신한다. 운영 업데이트는 깨끗한 체크아웃과 `git pull --ff-only`를 사용한다.
2. 해당 PC의 `.venv`, 비공개 DB 설정, MariaDB 데이터, 모델 파일은 그대로 유지한다. Git 갱신으로 DB 권한이나 추가 테이블이 자동 생성되지는 않는다.
3. 백업 후 `tube_plugging_event`, `customer_correction_event`와 보호 트리거의 적용 여부를 확인한다. 누락된 경우 기존 `migration/plugging_operations.py`의 명시적 마이그레이션을 해당 PC에서 적용한다. 고객 검사값 보정은 별도 작업이며 이 문서의 소스 반영만으로 실행하지 않는다.
4. Text-to-SQL 전용 계정의 현재 사양·검사 이력 SELECT 권한을 확인한다. 권한 추가는 해당 PC의 관리자 승인 범위 안에서 수행하고 쓰기 권한을 부여하지 않는다.
5. 위 읽기 전용 검증 도구와 기존 기동 방식으로 검증한다. 첫 화면과 Text-to-SQL 화면도 확인한다. 여러 웹 프로세스를 쓰는 경우 모델 대기열과 Excel 결과 보관은 프로세스별 메모리라는 제한을 고려한다.

비공개 설정, 백업, 세션, 업무 데이터, 원본 PDF·Excel, 모델 가중치 및 생성된 검증 보고서는 Git에 포함하지 않는다.
