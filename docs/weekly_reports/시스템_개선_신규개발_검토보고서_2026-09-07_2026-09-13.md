## 1. 종합 요약

보고 기간에는 Tube Layout의 운영 적용과 정합성 보정, 데이터 품질 감사·정상화, 계산 경계 강화, 모바일 Tube Map 개선, 읽기 전용 ML 분석 기반과 검토 화면 구축이 집중적으로 진행되었다.

현재 운영 DB의 핵심 무결성은 정상이다. 2026-09-13 재점검에서 SQLite `quick_check=ok`, 외래키 위반 0건을 확인했고, Python 3.13 기준 전체 자동 테스트 132건이 통과했다. 운영 Layout은 승인 61건·반려 2건이며, Layout Point는 검증 23,344건·반려 667건으로 미결 상태가 없다.

다만 시스템 전체 판정은 **조건부 적합**이다. 권한 설정 오류·누락, 자동 백업 실행 지연, 데이터 품질 잔여 603건, 원천 수량이 충돌하는 Layout 10건, 결함 원주각·길이 원천 부재, 실물 모바일 단말 검증 미수행, ML 추세모델의 예측구간 미달 및 전문가 라벨 부재가 남아 있다.

### 2.3 신규 개발 기능

#### A. Tube Layout 운영·관리

- `tube_layout_revision`과 `tube_layout_point` 기반의 원천 Layout 이력·좌표 관리 구조를 구축했다.
- Layout Revision 읽기 전용 관리 화면과 Tube Map 조회 경로를 추가했다.
- Pilot 적용, 일반 Rollout, U-Bend 별도 처리, 승인·검증·중복 정리 도구를 개발했다.
- Layout 원천 감사, 불일치 진단, 적용 계획, 승인 및 운영 검증을 단계별로 수행하는 도구를 추가했다.

#### B. ML 분석·검토

- 운영 DB 읽기 전용 연결, DB Hash 확인, Artifact 격리·원자적 저장 및 ML 의존성 점검 기능을 추가했다.
- 추적 가능한 데이터마트와 G1~G7 품질 Gate, 시간·설비·Tube 단위 누수 방지 검사를 구현했다.
- 이상치 우선순위 모델과 읽기 전용 검토 화면을 추가했다. Cohort A 6,084행을 대사했고 Hard Gate 중대 이슈 누락은 0건이다.
- 감육 추세 파일럿을 구현했다. 2025년 최종 검증 127건에서 기준 대비 MAE가 0.2249 mm에서 0.1091 mm로 약 51.5% 개선됐으나, 80% 예측구간 포함률은 30.7%로 Gate를 통과하지 못했다.
- 승인 Layout 전용 공간 Hotspot 파일럿과 검토 화면을 추가했다. 61개 승인 Revision, 57개 설비, 3,743개 결과를 분석했으며 미승인 Layout 사용과 좌표 오류는 0건이다.
- 다회 검사 Tube 1,435건을 유사 열화 패턴 3개 그룹으로 구성하고 검토 화면·도움말을 추가했다. Silhouette 0.503, Seed 안정성 ARI 1.0을 기록했다.

#### C. 감사·보고 자동화

- 주간보고서 DB 요약, DOCX 생성 및 2D/3D Tube Map 샘플 생성 기능을 개발했다.
- 데이터 품질 이슈와 Master 값 편차의 안전한 정리 대상을 분류하고 잔여 검토 CSV를 생성하는 도구를 추가했다.
- E-112 Count 의미 보정, E-106 중복 정리 및 E-331A 승인 계보 검증 도구를 추가했다.
- 모바일 Tube Map 자동 회귀 스크립트와 실기기 점검 체크리스트를 작성했다.

   - 모든 업무 Endpoint가 공개·관리자 전용·권한표 중 하나로 분류되는 자동검사를 추가한다.

| 세부 작업 | 내용 |

| 대상 선정 | 검사 결과가 존재하지만 점검요청 또는 승인 Data가 없는 설비·검사를 추출한다. |
| 생성 기준 | 검사일, 감육률, 판정, 품질 이슈, Tube 상태 등 현재 검사 결과에서 점검요청 사유와 우선순위를 결정한다. |
| 강제 생성 | 승인된 생성 규칙에 따라 점검요청 Data와 승인 Data를 Batch 단위로 생성한다. |
| 상태 연결 | 요청 → 검토 → 승인 상태의 연결관계, 요청자·승인자·처리시각·사유를 기록한다. |
| 중복 방지 | 동일 검사결과를 재실행해도 중복 요청이나 중복 승인이 생성되지 않도록 멱등성을 보장한다. |
| 검증 | 생성 전후 건수, 고아 Data, 외래키, 상태 전이, Dashboard 및 상세 화면 표시를 대사한다. |
| 복구 | 실행 전 Backup ID와 생성 Batch ID를 남기고 해당 Batch만 안전하게 되돌릴 수 있게 한다. |

산출물:

- 생성 대상 및 제외 대상 목록
- 점검요청·승인 Data 생성 규칙서
- Dry-run 결과와 실제 생성 결과
- 생성 전후 건수 및 상태 대사 보고서
- Batch 단위 Rollback 절차

완료 기준:

1. 대상 검사결과와 생성된 요청·승인 Data가 1:1로 추적된다.
2. 중복·고아 Data와 비정상 상태 전이가 0건이다.
3. 생성 Data가 관련 화면과 집계에 정상 표시된다.
4. 전체 자동 테스트, DB 무결성 및 외래키 검사가 통과한다.

### 6.2 Database Backup 자동화 및 Restore 자동화 Process 구현

| 구분 | 구현 내용 |
|---|---|
| Backup 스케줄 | 설정된 주기와 시각에 자동 실행하고 서비스 재기동 후 누락된 회차를 감지한다. |
| Backup 검증 | 생성 직후 파일 크기·Hash·SQLite 무결성·외래키 상태를 확인한다. |
| 보존정책 | 정상 검증된 Backup만 보존 수량에 포함하고 삭제 대상과 결과를 로그로 남긴다. |
| 실패 대응 | 실패 사유, 재시도 시각, 마지막 성공 Backup과 관리자 확인 필요 상태를 화면에 표시한다. |
| Restore 선택 | 관리자가 복구 대상 Backup과 복구 사유를 명시하고 실행 전 영향 범위를 확인한다. |
| Restore 보호 | 현재 DB를 사전 Backup한 후 쓰기 요청을 차단하고, 선택 파일을 임시 경로에서 먼저 검증한다. |
| 자동 복구 | 검증된 파일만 운영 DB로 교체하고 서비스 재기동·Health Check·핵심 조회를 자동 수행한다. |
| 감사 이력 | 실행자, 대상 파일, 이전·이후 Hash, 시작·종료 시각, 성공·실패·Rollback 결과를 저장한다. |

산출물:

- 자동 Backup 상태 감시 및 재시도 기능
- 관리자용 Restore 실행 Process
- 사전 Backup → 검증 → 교체 → 재기동 → Health Check 절차
- Backup/Restore 통합 테스트 및 운영 매뉴얼

완료 기준:

1. 예정 시각 자동 Backup과 누락 회차 보완 실행이 성공한다.
2. 손상 Backup은 Restore 전에 차단된다.
3. 정상 Backup 복구 후 DB 무결성, 외래키 및 핵심 화면 조회가 통과한다.
4. Restore 실패 시 사전 Backup으로 원상복구할 수 있다.
5. 모든 실행 결과가 감사 로그에 남는다.

완료 기준:

4. 기기·OS·브라우저별 결과와 화면 증적을 보존한다.

### 6.4 Data 분석에 ML 활용방안 검토

| 활용 후보 | 검토 내용 | 운영 적용 조건 |
|---|---|---|
| 이상치 우선순위 | 감육률·계산 불일치·품질 이슈를 결합해 검토 순서를 추천 | Hard Gate 누락 0건, 전문가 Precision 기준 충족 |
| 감육 추세 | 다년 검사결과를 이용해 다음 검사 두께·감육률 범위를 예측 | 시간 검증과 예측구간 포함률 Gate 충족 |
| 공간 Hotspot | 승인 Layout과 인접 Tube를 이용해 국부 부식 집중구역 탐색 | 미승인 좌표 사용 0건, 전문가 Top 30 확인 |
| 유사 열화 패턴 | 다회 검사 Tube를 안정·고감육·고변동 후보군으로 묶어 검토 지원 | 설명 가능한 특징과 전문가 라벨 확보 |
| Data 품질 탐지 | 원천·Master·계산식·반복 측정의 이상 조합을 자동 추천 | 원본 근거 링크와 오탐 검토 Workflow 확보 |
| 검사·정비 우선순위 | 감육·잔여수명·Hotspot·품질 상태를 종합해 검토 대상을 제시 | 자동 승인 금지, 엔지니어 최종판정 유지 |

검토 범위:

1. 업무 활용가치, 필요한 입력 Data와 현재 확보율을 평가한다.
2. 기존 규칙 기반 결과와 ML 결과를 동일 검토량으로 비교한다.
3. 정확도·재현율·과소 안전판정·설명가능성·실행시간 기준을 정한다.
4. 전문가 라벨 수집 방식과 검토·승인·반려 Workflow를 설계한다.
5. 모델 결과가 원본 측정값이나 승인 상태를 자동 변경하지 않도록 경계를 확정한다.

산출물:

- ML 활용 후보별 효과·Data 준비도·위험·난이도 비교표
- 우선 적용 대상과 보류 대상
- 전문가 검증용 표본 및 라벨 기준
- 단계별 PoC와 운영 적용 판단 기준

완료 기준:

1. 우선 적용할 ML Use Case와 제외할 Use Case가 구분된다.
2. 각 Use Case의 입력 Data, 품질 Gate, 평가 지표와 책임자가 정의된다.
3. 운영 자동판정 없이 검토지원으로 적용할 수 있는 범위가 확정된다.

## 7. 결론

전체 재검토 결과, 운영 DB 무결성과 핵심 기능 회귀는 정상이며 시스템의 기본 기능은 안정적으로 동작한다. 차주에는 현재 검사결과에서 점검요청·승인 Data를 생성해 실제 업무 흐름을 검증하고, 이에 앞서 안전한 복구 지점을 확보한다.

이후 Database Backup/Restore 자동화 Process, 모바일기기 최적화, ML 활용방안 검토를 순서대로 수행한다. ML은 자동판정이나 원본 변경 기능이 아니라 전문가의 Data 검토와 의사결정을 지원하는 범위에서 적용 가능성을 평가한다.
