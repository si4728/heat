## 1. 재점검 결론

원시자료는 DB 보강에 사용할 수 있다. 다만 파일에 보이는 숫자를 일괄 덮어쓰는 방식이 아니라, 원본 파일을 검사 레코드와 먼저 확정 매핑하고 출처·신뢰도·충돌 여부를 기록한 뒤 빈 필드만 채워야 한다.

### 갱신 범위

운영 DB 갱신 대상에 다음 영역을 포함한다.

1. `iris_tube_result`: 튜브별 최소두께, 위치, 감육깊이/감육률, 결함코드, 부식유형, 비고 등
2. `iris_indication`: 기존 튜브 결과에 종속되는 개별 결함의 위치·각도·길이·측정두께·감육값 등
3. `iris_inspection`: 위 튜브 결과를 반영해 다시 계산되는 결과 건수와 최소두께·최대/평균 감육률 등 결과 요약값
4. `inspection_execution_snapshot`, `iris_setup_snapshot`: 검사 장비, 교정, 취득/분석 소프트웨어와 검사 설정
5. `inspection_personnel`: 검사자, 판독자, 작성자와 소속 정보
6. `iris_tube_map`, `inspection_attachment`: 튜브맵 정보와 실제 첨부자료 존재·종류
7. `iris_recommendation`: 원보고서 또는 원시자료에 명시된 권고사항
8. `tube_degradation_assessment`: 검증된 검사결과를 기반으로 재계산한 감육속도와 잔여수명
9. `inspection_plan_v2`, `work_order_v2`, `maintenance_record`: 명시적 검사계획·작업지시·정비조치가 확인되는 경우의 연계정보

다음 영역은 기본적으로 **갱신하지 않는다**.

- 설비 및 교환기 마스터: `equipment`, `heat_exchanger`, `heat_exchanger_tube`, `tube_bundle`, `inspection_scope`

설비 마스터는 기존 식별자를 연결에 사용하되 자동으로 새 설비를 만들거나 기존 설비 속성을 덮어쓰지 않는다. 기존 `heat_exchanger_tube`에서 대응 튜브를 찾지 못한 원시 결과는 튜브 마스터를 임의 생성하지 않고 staging의 미매핑 결과로 남긴다. 작업지시·정비·권고는 원천에 명시된 내용만 허용하며 검사결과만으로 임의 생성하지 않는다.

### 2.6 튜브번호와 원시파일 매핑

파일명에서 튜브 행·열을 추출할 수 있다.

- 기본형 `RRRCCC`: 앞 3자리는 Row, 뒤 3자리는 Column이다. 예: `001005.tis2` 또는 `001005.magdata` → 튜브 `1-5`.
- `.magdata` 재수집형 `RRRCCC.001`: 기본 파일과 같은 튜브이며 재수집 순번을 별도로 기록한다. 29개 모두 기본 파일이 함께 존재한다.
- `.tis2` 재수집형 `RRCCCA`: `07016A.tis2` → Row 7, Column 16이다. 34개 모두 대응 기본 파일 `007016.tis2`가 함께 존재한다.
- `CAL-002003.magdata` 1개는 교정 파일이므로 튜브 결과에서 제외한다.

| 형식 | 전체 파일 | 튜브번호 해석 | 기존 튜브 마스터 연결 | 기존 검사결과 연결 |
|---|---:|---:|---:|---:|
| `.magdata` | 1,739 | 1,738 | 1,737 | 1,729 |
| `.tis2` | 826 | 826 | 746 | 743 |

`.magdata`의 튜브형 파일 1,738개 중 튜브 마스터에 없는 것은 VCM2 2025 E-222의 `019012.magdata` 1개다. 기존 검사결과와 연결되지 않는 9개는 신규 측정결과인지 추가/재수집 자료인지 별도 확인한다.

`.tis2`는 파일명 기준으로 모두 튜브번호를 알 수 있지만 80개는 현재 튜브 마스터에 없고 83개는 기존 `iris_tube_result`에 없다. 대부분 2023년 VCM1 E-201A-D/E-211A-D 폴더군에 집중되어 있어 장비 간 자료 혼재 또는 PDF 결과 미수록 여부를 교차 검증해야 한다. 이 파일들은 자동으로 튜브나 결과를 생성하지 않고 staging의 `UNMATCHED_TUBE` 또는 `NO_EXISTING_RESULT` 상태로 관리한다.

한 튜브에 기본파일과 재수집파일이 함께 있을 수 있으므로 관계는 `튜브 1 : 원시파일 N`으로 설계한다. 기본키는 검사 ID·튜브 ID·원본 상대경로이며, 재수집 순번을 별도 속성으로 둔다.

## 3. 검사이력 연계정보 갱신 우선순위

DB는 `quick_check=ok`, 외래키 위반 0건이다. 검사결과를 먼저 확정한 뒤 수행정보와 후속 관리정보를 순차적으로 갱신한다.

### 우선순위 A: 기존 튜브 결과의 빈 필드 보강

| 대상 필드 | 현재 입력 | 허용 원천 |
|---|---:|---|
| `iris_tube_result.minimum_wall_thickness_mm` | 5,805/6,084 | CSV RESULT/DETAIL, MDB result/tubeFeature |
| `iris_tube_result.location_mm` | 5,739/6,084 | CSV RESULT/DETAIL, MDB result/tubeFeature |
| `iris_tube_result.remark` | 288/6,084 | CSV Comments, MDB comment |
| `iris_tube_result.design_wall_thickness_mm` | 1,326/6,084 | 명시된 원천 규격값만 허용 |
| `iris_tube_result.defect_code` | 1,326/6,084 | CSV DamageType, MDB defect/eval의 의미 검증 후 |
| `iris_tube_result.reported_depth_percent` | 1,326/6,084 | CSV SurfacePercent 또는 명시된 보고값 |

기존 값이 있는 행은 자동으로 덮어쓰지 않는다. 원시자료 범위에 연결된 163개 검사 안에서 검사 ID와 튜브 ID가 모두 확정되고 대상 필드가 비어 있는 경우만 갱신 후보가 된다.

### 우선순위 B: 개별 결함 상세 신규 생성

- `iris_indication`은 현재 0건이다.
- MDB `result`/`tubeFeature`와 CSV DETAIL을 중복 제거해 후보를 만든다.
- 기존 `iris_tube_result_id`가 확정된 결함만 INSERT한다.
- 축방향 위치, 원주각, 결함유형, 길이, 측정두께, 감육깊이/감육률, 판정과 원본 경로를 저장할 수 있다.
- 대응 튜브 결과가 없으면 `iris_tube_result`를 임의 생성하지 않고 미매핑 목록으로 남긴다.

### 우선순위 C: 검사 결과 요약 재계산

튜브별 결과 반영이 끝난 검사에 한해서 다음 `iris_inspection` 결과 요약값을 재계산 후보로 만든다.

- `extracted_tube_result_count`
- `reported_minimum_thickness_mm`
- `reported_maximum_wall_loss_percent`
- `reported_average_wall_loss_percent`

명칭에 `reported_`가 포함된 값은 PDF 보고값과 계산값을 구분해야 한다. 기존 보고값은 보존하고, 재계산 결과가 다르면 자동 변경하지 않고 품질 이슈로 기록하는 것을 기본 원칙으로 한다.

### 우선순위 D: 검사 장비·교정·소프트웨어·인력 정보

- `inspection_execution_snapshot`: 계약번호, 작업지시번호, 절차서/개정번호, 취득·분석 소프트웨어, 장비 교정일/유효기간, 비고
- `iris_setup_snapshot`: 검사장비 및 탐촉자 제조사·모델·일련번호, 주파수, 재질속도, 주사속도, 수압·수온
- `inspection_personnel`: CSV Technician과 MDB operator/analyst를 검사자·판독자 역할로 구분
- `.magdata` 887개에서 확인된 소프트웨어·장비번호·교정일과 CSV 162개 결과행의 장비/탐촉자/터빈 번호·기술자·세션 정보를 사용
- 동일 검사에 원시파일이 여러 개이면 파일별 값을 먼저 집계하고 전 파일이 일치하거나 대표값 선정 규칙이 확인된 경우만 검사 스냅샷에 반영
- 교정 유효기간은 명시된 값 또는 승인된 산정규칙이 있을 때만 입력

### 우선순위 E: 튜브맵·첨부파일

- `iris_tube_map`: orientation 35/435, 간격 260/435, total_tubes 394/435 등 기존 결측을 MDB section과 CSV MAP으로 보강
- 2025년 MAP CSV 20개의 3,408개 `tube_id/x/y` 행은 좌표 근거로 활용
- `inspection_attachment`: 실제 PDF·PNG·BMP·JPG의 존재, 유형, 원본 경로와 검사 연결을 확인해 `attachment_present`와 유형 정보를 보강
- 첨부파일은 운영 DB에 바이너리로 넣지 않고 경로·해시·유형을 관리하는 방식을 우선 적용

### 우선순위 F: 정비·수명예측·권고·작업지시

- `iris_recommendation`: 원보고서나 원시 결과에 명시된 권고문만 추가·대조하고 기존 1,448건은 자동 덮어쓰지 않음
- `tube_degradation_assessment`: 변경된 튜브 결과와 이전 검사결과가 모두 유효할 때만 영향받은 튜브를 재계산하고 알고리즘 버전과 계산근거를 보존
- `inspection_plan_v2`: 검사완료 연결이나 차기 검사계획이 명시된 경우에만 기존 435건을 보강
- `work_order_v2`, `maintenance_record`: 현재 각각 0건이므로 원천에 작업번호·조치일·조치내용이 명시된 경우만 신규 생성
- 검사결과의 감육률만으로 작업지시나 정비완료 기록을 자동 생성하지 않음

### 입력 제한 및 보류

- 2023년 TUBE_STATUS CSV의 `MinWallThickness=0`, `WallLoss=0`: 전 행이 미검사 초기 상태이므로 결과값으로 사용 금지
- `iris_tube_result.raw_side`: 원천 의미가 확정되기 전까지 보류
- `iris_tube_result.analysis_v`: MDB volts와 같은 의미인지 확인되지 않아 보류
- 설비·교환기·튜브 마스터: 자동 생성 및 자동 덮어쓰기 금지
- 정비·권고·작업지시: 명시적 원천 없이 계산 또는 추정만으로 신규 생성 금지
- `Report.mdb`: 암호 또는 제조사 내보내기 기능을 확보하기 전에는 제외
- `.tis2` 및 `.magdata` 파형 배열: 제조사 SDK 또는 검증된 파서 없이는 수치화 금지

## 4. 매핑 규칙

매핑 기본키는 `공장 + 검사연도 + 표준 장비코드 + 번들 + 검사범위`이다.

1. 폴더명에서 `VCM1/VCM2`, 장비코드, 날짜, 번들, 범위, 검사 차수, 추가/재수집 여부를 각각 분리한다.
2. 날짜는 `YYMMDD` 또는 `YYYYMMDD`만 자동 확정한다. 과거 7자리 오기처럼 유효하지 않은 날짜는 자동 변환하지 않고 예외 규칙 또는 검토 이력을 요구한다.
3. `BOTTOM`, `BTM`, `BOM`은 원문을 보존하면서 표준값 `BTM`으로 매핑한다.
4. `AE-502B1`, `AE-502B-1`은 장비 `AE-502B`, 번들 `1`로 분리한다.
5. `E-332-1/2`도 장비와 번들을 분리한다.
6. 추가 수집·재수집·1차/2차/3차는 새 검사를 만들지 않고 원시 파일의 `acquisition_group` 또는 `rescan_sequence`로 기록한다.
7. VCM2 원시 파일 내부의 `E-162A/B`, `E-502A-D` 표기는 DB의 승인된 `AE-*` 장비 별칭으로 처리하되 원문도 저장한다.

수동 검토가 필요한 확인된 충돌:

- `VCM1\2025\E-340A\MAP` 안의 파일명이 `E-304A CARTO`임
- `VCM2\2025\E-302`의 일부 설정/원시파일에 `VCM1` 문자열이 존재함
- `VCM1\2023\VCM1-E-201D(231114)`에 `E-211A-D` 보고서 PDF가 함께 존재함
- 폴더 장비코드와 파일 내부 장비코드가 다른 경우 폴더만 믿지 않고 외부 `mapping_conflicts.csv`에 기록함

## 5. 검사이력 통합 staging 구조

첫 반영에서는 운영 DB 스키마를 추가하지 않고 별도 SQLite staging DB 또는 CSV/JSON 산출물을 사용한다. staging에는 다음 구조가 필요하다.

### `raw_extraction_batch`

- 실행 ID, 실행 시각, 파서 버전, 대상 루트, 대상 DB 해시, 상태, 오류 수

### `raw_inspection_file`

- `iris_inspection_id`
- 원본 상대경로, 확장자, 크기, 수정시각, SHA-256
- 원본 튜브 표기, Row/Col, 번들, 범위, 재수집 순번
- 검사결과 원본 파일 경로와 취득일시
- 취득/분석 소프트웨어, 검사장비·탐촉자·터빈 정보, 교정일
- 검사자/판독자, 계약·절차서, 튜브맵·첨부·권고·조치 원문
- 추출 상태, 신뢰도, 파서 버전, 오류 메시지

### `raw_observation_staging`

- 원천 파일/테이블/행 식별자
- 대상 테이블/컬럼 후보
- 원천값, 정규화값, 단위, 변환 규칙
- 매핑된 검사/튜브 ID
- 신뢰도, 충돌 상태, 검토 상태

운영 DB 반영 SQL은 1절에 명시한 검사이력 연계 테이블만 변경하도록 허용 목록을 코드에서 강제한다. 설비 마스터 테이블은 허용 목록에서 제외한다.

## 6. 단계별 수행계획

### 0단계: 입력 동결 및 복구점 확보

- VCM1/VCM2 전체 파일 manifest 작성: 상대경로, 크기, 수정시각, SHA-256
- 현재 DB의 SQLite 온라인 백업 생성
- 백업 DB에 `quick_check`와 `foreign_key_check` 수행
- 원본 폴더는 읽기 전용으로 취급

완료 기준: 원본과 DB의 재현 가능한 기준 해시 및 복구점이 존재한다.

### 1단계: 폴더/검사 매핑 dry-run

- 169개 폴더를 구조화해 163개 검사 레코드와 연결
- 번들/범위/재수집 분리
- 단일 후보, 규칙 확정, 수동 검토의 세 등급으로 분류
- 위 4개 확인된 충돌을 품질 이슈 후보로 출력

완료 기준: 미매핑 0건, 다중 후보 미해결 0건, 각 매핑에 근거 문자열이 존재한다.

### 2단계: 원시자료 추출기 구현

추출 순서는 구조가 명확한 형식부터 진행한다.

1. CSV RESULT/DETAIL/TUBE_STATUS/MAP
2. MAP/CARTO MDB의 inspection/section/tube/result/tubeFeature
3. FolderDescription XML을 이용한 원본 파일-튜브 연결
4. `.magdata`와 `.magsetup`의 취득시각·소프트웨어·장비·교정 메타데이터
5. PDF·PNG·BMP·JPG 첨부파일의 유형·경로·해시
6. 보고서/MDB/CSV의 권고·정비·작업지시 원문
7. `.tis2`는 검증된 포맷 파서 확보 전까지 파일 메타데이터와 튜브 연결만 등록

완료 기준: 동일 입력을 두 번 실행했을 때 동일한 staging 결과와 해시가 생성된다.

### 3단계: 단위·의미 정규화

- 위치와 길이의 m/mm 단위를 명시적으로 변환
- 감육깊이(mm), 감육률(%), 잔존률(%)을 구분
- 취득일시는 원본값, 정규화값, 시간대를 함께 보존
- `0`, 빈 문자열, NULL, 미검사 상태를 서로 구분
- 결함 코드와 부식 유형은 원문과 정규화값을 함께 보존
- 장비 주파수와 데이터 취득률을 구분하고 Hz/MHz 단위를 확인
- 주사속도, 재질속도, 수압·수온의 원천 단위와 DB 단위를 명시적으로 변환
- 검사자·판독자·작성자 역할을 혼합하지 않고 원문 역할을 보존

완료 기준: 각 변환 필드에 단위와 변환 규칙이 기록되고 역추적 가능하다.

### 4단계: 대조 및 충돌 검출

- PDF/기존 DB/원시자료를 필드별로 비교
- 기존 값과 같은 값: 일치 근거만 추가
- 기존 값이 NULL인 경우: 고신뢰 원천만 보강 후보 지정
- 기존 값과 다른 경우: 자동 덮어쓰기 금지, 외부 충돌 목록 생성
- 숫자 0은 상태 필드와 함께 해석하여 결측 대용 0인지 실제 0인지 판정

완료 기준: 변경 후보마다 before/after/source/confidence가 있으며 충돌 건수와 목록이 산출된다.

### 5단계: 표본 검증

공장·연도·파일 형식별 표본을 선정한다.

- VCM1/VCM2 각각 2021, 2023, 2025 최소 1개
- 번들형 1개, TOP/BTM형 1개, 재수집형 1개
- MDB result가 있는 검사와 CSV RESULT가 있는 검사 각 1개 이상
- 장비코드 충돌 사례 3개 전부

완료 기준: 표본의 폴더→파일→튜브→DB 값이 수작업으로 재현되고 단위·날짜·식별자가 일치한다.

### 6단계: 승인용 변경안 생성

- 실제 UPDATE/INSERT 전 변경 예정 CSV 또는 JSON 생성
- 테이블별 INSERT/UPDATE 수, 제외 수, 충돌 수 집계
- `iris_indication`은 기존 `iris_tube_result_id`가 확정된 행만 포함
- 장비/교정/인력, 튜브맵/첨부, 권고/예측/계획/작업/정비 변경안을 영역별로 분리
- 수명예측은 입력 결과 변경과 재계산 결과를 함께 제시
- 작업지시·정비 기록은 해당 원문 근거를 각 행에 첨부
- 동일 파일/동일 원천행을 재실행해도 중복 생성되지 않는 고유키 정의

완료 기준: DB를 변경하지 않고 최종 반영 결과를 검토할 수 있다.

### 7단계: 트랜잭션 반영

- 승인된 dry-run만 단일 트랜잭션으로 반영
- SQL 허용 대상은 1절의 검사이력 연계 테이블로 제한하고 설비 마스터 테이블은 차단
- 기존 비NULL 값을 기본적으로 보존
- 반영 직후 무결성 검사, 행 수 비교, 샘플 조회 수행
- 허용 대상 외 테이블의 변경 건수가 0인지 확인
- 실패 시 전체 롤백

완료 기준: `quick_check=ok`, 외래키 위반 0건, 승인된 변경 수와 실제 변경 수가 일치하고 대상 외 테이블 변경이 0건이다.

### 8단계: 사후 검증 및 운영화

- 반영 전후 결측률 비교
- 원본 파일 누락/변경 감지 리포트 생성
- 파서 회귀 테스트와 고정 표본 테스트 추가
- 실행 로그와 추출 버전을 운영 DB 밖의 감사 파일로 보존

완료 기준: 같은 입력을 재실행해 신규 변경 0건이 되는 멱등성이 확인된다.
